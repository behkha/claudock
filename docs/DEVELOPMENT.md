# Developing Claudock

The build spec is [SPEC.md](SPEC.md).

## Setup

Node 22.12 or later (Electron 45 and Vite 8 require it).

```sh
npm install
npm run fixture   # builds ./.fixture/claude, a synthetic config folder
npm run dev       # runs the app on the fixture
```

## The fixture rule

**Development and tests never write to the real `~/.claude`.** `npm run dev` sets `CLAUDE_CONFIG_DIR=./.fixture/claude`; `npm run shot` copies the fixture into a temp home as `~/.claude` (and `./.fixture/claude-work` as `~/.claude-work`) and points `CLAUDE_CONFIG_DIR` there. A build run from the git clone also refuses every write unless the open folder is the one `CLAUDE_CONFIG_DIR` named or a synthetic one (a `.claudock-fixture` file in it, which the fixture generators and a development build's "New folder" write), or `CLAUDOCK_ALLOW_REAL_WRITES=1` is set, so `npm run dev:real` is a read-only look at your own folder. Installers and the npm copy (`npx claudock`: an app folder inside a `node_modules`, or on macOS the `Claudock.app` built from one, marked by `claudock-npm-copy.json`) write normally (`installKind()` in `src/main/paths.ts`). The fixture is generated from scratch by `src/main/demo/fixture.ts`, with a smaller second account beside it (`./.fixture/claude-work`, `src/main/demo/workFixture.ts`) for profiles; nothing is copied from a real config. `.credentials.json` there contains `FAKE-DO-NOT-READ` on purpose. The same generator backs `--demo` (`npx claudock --demo`, or `--demo` on an installed app; `src/main/demo/index.ts`): app data goes in a "Claudock Demo" folder beside "Claudock", so it has its own snapshots, prefs and single-instance lock and runs next to the real copy, and the fixture is rebuilt in `<that folder>/claude` (and `claude-work` beside it) on every launch with paths pointing there. Open at login is off in the demo.

All writes to the user's config go through `src/main/safeWrite.ts` (snapshot to `<userData>/snapshots`, temp file + atomic rename, JSON validated, deletes to the OS Trash). Claudock's own data is written directly (temp file + rename) and never snapshotted: `<userData>/prefs.json` (theme, the alert settings and whether the menu bar item is shown), the cache of the settings docs, `<userData>/settings-docs.json`, the connect folder, `<userData>/connect/<config dir hash>/`, what Context's switches put back, `<userData>/context/<config dir hash>.json` (`context.dev` in a git clone), and the session archive, `<userData>/archive/<config dir hash>/` (`archive.dev` in a git clone). "Connect to Claude Code" (`src/main/domains/connect.ts`) adds two parts to settings.json in one safeWrite (snapshot, atomic write, under the settings.json lock): the live limits status line step (`statusline.sh`, which Claude Code runs as the status line and which saves the last `rate_limits` to `limits.json`; `src/main/domains/limits.ts`. Only terminal sessions run the status line: sessions in the Claude desktop app never do, so each limit falls back to Claude Code's `quotaLimits` record of a refused request ("Limit reached" until it resets) and then to that window's tokens, `limitShown()` in `src/shared/limits.ts`) and nine session hooks that run `hook.sh` (`src/main/connect/hookScript.ts`) and append one line per event to `sessions/<session id>.jsonl`; Claudock works out from those lines whether the session is working (and the last tool it finished), waiting for you or done (`src/main/connect/sessionModel.ts`, read by `src/main/domains/sessions.ts`, which also posts the waiting alert and names each session from its transcript: the newest `custom-title` line, else its first prompt, `ownSessionName()` in `src/main/domains/projects.ts`). `state.json` there keeps the previous `statusLine`, what the hooks created, and the snapshot Disconnect uses to put settings.json back byte for byte when nothing else changed it. Disconnect leaves `hook.sh` as a no-op and `statusline.sh` in place, for sessions that run them until Claude Code reloads settings.json. `.credentials.json` and `sessions/*.key` are never read.

Profiles (`src/main/domains/profiles.ts`, pure parts in `src/main/profiles/model.ts`) are kept in `<userData>/profiles.json` (`profiles.dev.json` in a git clone, so `npm run dev` never lists an installed copy's real folders): `{ open, legacy, profiles: [{ name, dir }] }`, written directly like prefs.json (`legacy`: the launch folder when profiles first loaded, which owns the snapshots taken before profiles). `loadProfiles()` runs before the domains register and opens the right folder with `setConfigDir()` (`src/main/paths.ts`); modules that cache per folder clear themselves through `onConfigDirChanged()`. Every IPC call works on the folder open when it started, to its end (`withConfigDir()`, applied in `defineDomain`), so a write under way when another profile opens finishes in its own folder; code that asks which folder the window shows uses `openConfigDir()`. Sessions and limits keep one watch per profile folder (`watchFolders()` in sessions.ts, `watchLimitFolders()` in limits.ts), so the menu bar and the alerts cover every profile; `currentGlance()` puts them together for the menu bar and the title bar menu (`profiles:glance`). Each profile has its own connect folder, `<userData>/connect/<folder key>/`, whose name is also the profile's id. Add profile looks for folders named like the launch folder beside it (`.claude-*` beside `~/.claude`; `claude-*` beside the fixture and `--demo`'s folder), and `add()` takes only a folder it offered (found or picked) or a new one it makes. The renderer remounts the shell when another profile opens (`src/renderer/App.tsx`); the switcher is `src/renderer/shell/ProfileMenu.tsx` and the sheet `AddProfile.tsx`.

The menu bar item (`src/main/menubar.ts`; the tray on Windows and Linux) shows the higher of the two limits and swaps its template icon for a clay one while a session waits (`src/main/menubar/glance.ts`). Clicking it opens the popover, a second renderer page (`src/renderer/popover.html`, `src/renderer/popover/`) in a frameless window under the item; the limit alerts run there too (`src/main/menubar/limitAlert.ts`). With the item shown, closing the main window keeps Claudock running on macOS (hiding the Dock icon, `src/main/windows.ts`) and Windows; Linux quits as before. Open at login (`src/main/loginItem.ts`) writes `~/Library/LaunchAgents/app.claudock.login.plist` (macOS) or `~/.config/autostart/claudock.desktop` (Linux) only when turned on, and starts the app with `--login`: the menu bar item without a window. It is offered only to a copy with a fixed path: never a git clone, npx's cache, a mounted disk image or a translocated app. On macOS `npx claudock` runs `<userData>/Claudock.app` (`bin/macApp.js`): npm's Electron cloned, renamed (bundle id `app.claudock.npm`, apart from the installer's `app.claudock`), with the app folder inside and signed ad hoc, rebuilt when Electron or the build changes; `claudock-npm-copy.json` in its app folder makes `installKind()` say `npm`. `CLAUDOCK_PLAIN_ELECTRON=1` skips it. The menu bar icons are drawn by `npm run icons` from `build/tray*.svg`.

The session archive (`src/main/domains/archive.ts`, the Sessions screen in `src/renderer/screens/Sessions/`; screen id and domain `archive`, since `sessions` is the live "needs me" domain) keeps every transcript Claude Code's cleanup would delete. Per profile folder, `<userData>/archive/<folder key>/` (the connect folder's key; `archive.dev` in a git clone, so `npm run dev:real` never touches the archive an installed copy keeps) holds `projects/<project>/<id>.jsonl` and the session's `<id>/` folder, hard-linked to Claude Code's files where the disk allows, else copied and then appended to (`hold()` in `src/main/archive/hold.ts`; a held file only the archive has that the live one doesn't start with is first kept beside it as `<id>.<ms>.jsonl`, which then lists as its own archived session); `text/<project>/<id>.txt`, one line per prompt or reply (`<byte offset>\t<u|a>\t<text>`) for search; and `index.json`, what is known per session (size, inode, how far it was read, title, folder, first and last message, whether Claude Code's file is gone). The archive's own `projects/` is the truth: a session the index lost comes back on the next sweep. A sweep first holds every transcript and marks the ones Claude Code deleted (every profile at once), then reads what is new for search, newest first, one profile at a time; it runs 4 s after launch, every 10 minutes over every profile (`watchArchiveFolders()`, from profiles.ts), when another profile opens and when the Sessions screen lists (`list()` waits up to 3 s for the holding pass). The holding pass, each transcript read, and every change from the screen or Projects run one at a time per folder (`locked()`), so a session moved to the Trash never comes back from a sweep that listed it a moment before. Search reads the text files (kept in memory up to about 48M characters; one session over a quarter of that is read each time) and matches with `matchSession()` in `src/main/archive/model.ts`, which also builds the Markdown export and the resume command. Copy resume command puts a deleted session back with `placeNewFile()` (`src/main/safeWrite.ts`: linked or copied, never over an existing file, dated now so Claude Code's cleanup counts from today) and writes the clipboard from the main process (not in screenshot mode). Letting go of archive files goes through `unhold()`: a file with another hard link (Claude Code's, or the one in the Trash after a delete) or a copy that Claude Code's file still starts with is removed; anything else only the archive has is kept (archiving stopped) or sent to the Trash (`discard()`: gathered into one folder, one Trash item, moved back if the Trash fails). Move to Trash sends Claude Code's files to the Trash, then discards the archive's. When Projects trashes sessions (`onSessionsTrashed()` in projects.ts) the archive discards those too; when archiving stops, the archived sessions stay unless the user chose to send them to the Trash. A development build archives only folders it may write (`writesAllowed(dir)`) and never lets go of links it didn't make; Move to Trash and stopping are refused there. Transcript lines and entries are read by `src/main/transcripts/parse.ts`, shared with Projects.

The Context screen (`src/main/domains/context.ts`, `src/renderer/screens/Context/`; pure parts in `src/main/context/model.ts`, tested in `context.test.ts`) measures what each skill, MCP server and CLAUDE.md file adds to every session from what Claude Code records at a session's start, in the newest of the open profile's last 12 main transcripts that has it: attachment lines `skill_listing` (one `- name: description` line per skill Claude sees; `isInitial: false` adds to it), `deferred_tools_delta` (the tool names Claude can search for, `mcp__<server>__<tool>`, and the servers that failed, need a login or are still connecting), `mcp_instructions_delta` (each server's instructions) and `instructions` (every CLAUDE.md and rules file it loaded; type `User` is the profile's own; a later record with `changed: true` lists only the files that changed). A skill no session listed yet counts as SKILL.md would give it (name and description, the description capped at 1,536 characters); one that won't load (its plugin is off, `disable-model-invocation`) is left out; a server without a tool list has no number; this folder's CLAUDE.md and rules count as they are on disk now (one deleted since is gone, a rule with `paths:` loads later, so it is left out) and files from elsewhere (imports) as the session loaded them. Tokens are characters ÷ 3.5 (`estimateTokens()` in `src/shared/api/context.ts`). Used comes from `skillUsage` in the global state file (by the skill's own key) and from the MCP tool calls in the last 30 days of transcripts (sub-agents too, each call once by its id). Transcripts are read incrementally (`src/main/context/scan.ts`: on from where the last read stopped, symlinks skipped; for calls only the lines holding `"name":"mcp__` are parsed), one scan at a time per folder, and a finished scan is reused for 5 s; the sidebar badge skips the usage scan. Synced skills load only in the Claude app's sessions, listed as `<prefix>:<name>`, while the Skills screen keys their overrides by the bare name, so Context shows their cost without a switch. The switches write settings.json through `updateSettings` (snapshot, atomic write): `skillOverrides` (`switchSkill()`: off is `user-invocable-only`, on puts back the `on` or `name-only` it replaced) and `deniedMcpServers` (`switchServer()`: a `{ serverName }` entry), and `<userData>/context/<folder key>.json` (`context.dev` in a git clone) remembers what to put back and which containers a switch created, so turning something off and on again leaves settings.json byte for byte as before (as safeWrite writes JSON: 2-space indentation). Renaming a server keeps it off. Only a listed row with a switch can be switched. The fixture's recent sessions carry the four records (with a `github` server, a claude.ai connector that needs a login and one that loaded), a few MCP tool calls and `skillUsage`.

Today, the home screen (`src/renderer/screens/Today/`), shows the running sessions and limits (the card in `NowCard.tsx`), then today's other sessions and the last 7 days of tokens from `today.get()` (`src/main/domains/today.ts`), which sums the limits transcript scan (`transcriptUsage()` in `src/main/domains/limits.ts`, summed in `src/main/today/activity.ts`). The fixture's recent sessions carry Claude Code's `custom-title` lines, so names show in `npm run dev`.

The first-run reveal (`src/renderer/shell/Reveal.tsx`) replaces the sidebar and the screen while `system.firstRun()` says so: `revealed` is not set in prefs.json and neither Connect part is on (`src/main/firstRun.ts`). Screenshot mode never shows it on its own. `CLAUDOCK_REVEAL=1 npm run dev` shows it on every launch, connected or not, and doesn't write `revealed`; without it, delete `revealed` from `<userData>/prefs.json` to see it again.

At launch the main process downloads Anthropic's settings docs for the Settings JSON editor (`src/main/settingsDocs.ts`). `CLAUDOCK_OFFLINE=1` skips that fetch, so the editor uses the cache or the copy bundled with the app (screenshots skip it too). Installed copies also check for a newer release to show a new-version notice (`src/main/update.ts`): a stable build asks GitHub for the latest release, a beta build (a version with `-`) asks npm for the `latest` and `beta` dist-tags. `CLAUDOCK_OFFLINE=1` skips that too. `CLAUDOCK_LATEST_VERSION=9.9.9 npm run dev` shows the notice without a request (a pre-release value counts as the newest beta, so a stable build ignores it).

The one-line install scripts live on the site: `site/install.sh` (macOS: the DMG's app into `/Applications`, or `~/Applications`; Linux: the AppImage into `~/.local/bin/claudock`) and `site/install.ps1` (Windows: runs the Setup EXE). They build the download URL from the latest release's tag and the `artifactName` patterns in `electron-builder.yml`, so a renamed installer needs the scripts changed too. `CLAUDOCK_VERSION=0.1.1` pins a release and `CLAUDOCK_INSTALL_DIR=<folder>` installs somewhere else (install.sh only), which is how to try one without touching `/Applications`.

## Scripts

| Script | What it does |
|---|---|
| `npm run dev` | Dev server + Electron on the fixture |
| `npm run dev:real` | Same on your real folder, writes disabled |
| `npm run build` | Production build into `./out` |
| `npm run typecheck` / `npm run lint` | tsc (main + renderer) / ESLint |
| `npm test` | Unit tests (`src/**/*.test.ts`) with Node's test runner |
| `npm run fixture` | Rebuild `./.fixture/claude` and `./.fixture/claude-work` (Node runs `src/main/demo/fixture.ts` and `workFixture.ts` with `--experimental-strip-types`) |
| `npm run fixture:hooks` | After "Connect to Claude Code" in `npm run dev`: plays three Claude Code sessions through the fixture's hooks (one waiting on a permission prompt, one working that finishes a tool every 6 s, one done) and keeps them alive until Ctrl+C (`-- --group`: all three wait at once, for the grouped alert) |
| `npm run fixture:status` | Plays Claude Code calling the fixture's status line once with sample `rate_limits` (`-- --five 80`, `--week`, `--no-limits`, `--expired`) |
| `npm run shot` | Headless screenshots of every screen, light and dark, into `./.shots`. `-- --only skills,palette`, `-- --out <dir>`. `connect` runs Connect, plays the hooks, checks for exactly one alert, then Disconnect, and fails unless settings.json is byte for byte as before. `menubar` shoots the popover and its settings view on a connected fixture and checks the limit alert posts once at 85% and not again at 90%. `profiles` connects, adds `~/.claude-work` from the Add profile sheet, shoots the sheet, the title bar menu with both profiles and the popover, then switches back, disconnects and removes the profile, failing unless settings.json is byte for byte as before. `reveal` shoots the first-run reveal, the Connect sheet over it, Today after Connect and (light) the version with no stats, and fails unless settings.json is byte for byte as before. `context` checks the Context screen's numbers against the fixture's newest session, turns the github server and the db-migrations and release-notes skills off from their switches (`context-off`, with docs-search's counted text open) and back on, failing unless settings.json is byte for byte as before. `archive` (the Sessions screen) deletes the oldest session's transcript from the copy as Claude Code's cleanup would, finds it by a word of its title (`archive-search`) and resumes it (`archive-resume`), failing unless it was hard-linked, shows as Archived, comes back byte for byte dated now and exports to Markdown with its title |
| `npm run record` | The launch film's takes (`src/main/record.ts`) on a fresh fixture, light and dark (`-- --only light`), into `./.shots/record`: each take as a 60 fps MP4 recorded from the app's own window, slowed to an eighth so no frame is missed, with its frame times, clicks and cues in a JSON file beside it; the six screenshots in `stills/` (2560×1440) and `stills/1080/`; and the status line output, menu bar title and alert texts the film draws, in `strings.json`. The film itself is put together outside this repo |
| `npm run settings-docs` | Re-downloads Anthropic's settings docs and JSON schema and rebuilds `src/main/settingsDocs.bundled.json`, the offline fallback for the JSON editor's suggestions. Run it before a release |
| `npm run dist:mac` / `dist:win` / `dist:linux` | electron-builder packages into `./dist` |

## Layout

```
src/shared     IPC contracts (api/<domain>.ts), nav, types, format and frontmatter helpers
src/main       windows, menu bar, menu, paths, safeWrite, fsx, domains/<domain>.ts (one file per domain)
src/preload    generic bridge, no per-method code
src/renderer   shell, components, lib, screens/<Screen>/index.tsx, popover/ (the menu bar popover, its own page)
```

### Adding an IPC method to a domain

1. Declare it in `src/shared/api/<domain>.ts` (`export interface SkillsApi { list(): Promise<SkillInfo[]> }`).
2. Implement it in `src/main/domains/<domain>.ts` inside `defineDomain(ipcMain, '<domain>', { ... })`. The object must satisfy the whole interface.
3. Call it from the screen: `const { data, error, loading, reload } = useApi(() => api.skills.list(), [])`.

Events from main to renderer: add `'<domain>:<name>': Payload` to `<Domain>Events`, send with `emit(...)` from `src/main/ipcx.ts`, receive with `useEvent(...)`.
